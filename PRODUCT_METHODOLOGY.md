# Product Methodology

## Назначение

`call-analyzer-codex` — это система речевой аналитики звонков менеджеров по продажам недвижимости, которая:

- оценивает качество обработки звонка
- определяет исход звонка для воронки
- определяет, была ли предложена и согласована встреча
- выявляет оценочный резерв конверсии
- формирует управленческий и доказательный отчёт

## Источник истины

Источник истины в продукте — не “мнение модели”, а:

- фиксированная продуктовая рубрика
- жёсткие правила интерпретации фактов
- подтверждённые признаки из звонка
- экспертная валидация спорных случаев

## Основной принцип

Система должна:

- либо давать достаточно уверенный и доказуемый вывод
- либо помечать звонок как `Требует экспертной верификации`

Система не должна:

- маскировать сомнение под уверенный вывод
- искусственно улучшать KPI
- смешивать исключённые звонки с основной воронкой

## Единица анализа

Базовая единица анализа — один звонок.

Для каждого звонка система хранит:

- транскрипт
- извлечённые факты
- нормализованные сущности
- итоговую оценку
- флаги отчёта
- статус воронки

## Предметный диалог

Звонок считается предметным, если подтверждены хотя бы `2` из `5` блоков:

1. потребность
2. бюджет
3. способ оплаты
4. конкретный объект / ЖК
5. следующий шаг

### Что входит в эти блоки

#### Потребность

- тип жилья
- площадь
- район / ЖК
- цель покупки
- семейный контекст

#### Бюджет

- бюджет обсуждался явно

#### Способ оплаты

- ипотека
- рассрочка
- наличные
- смешанная форма оплаты

#### Конкретный объект / ЖК

- обсуждался конкретный объект
- обсуждался конкретный проект

#### Следующий шаг

- договорённость о повторном звонке
- договорённость о встрече
- договорённость об онлайн-консультации

## Статусы звонка

### `in_funnel`

Звонок входит в основную воронку.

### `out_of_funnel_non_target`

Звонок исключается из основной воронки, если:

- он нецелевой
- или это сервисный звонок по уже существующей записи / просмотру / процессу

### `out_of_funnel_callback_later_no_dialog`

Звонок исключается из основной воронки, если:

- клиент попросил вернуться к разговору позже
- предметного диалога не было

### `out_of_funnel_interrupted`

Звонок исключается из основной воронки, если:

- разговор прервался не по вине менеджера
- предметного диалога не было

### `out_of_funnel_interrupted_after_dialog`

Звонок исключается из основной воронки, если:

- предметный диалог уже начался
- разговор оборвался не по вине менеджера
- сценарий продажи не был завершён

## Что не должно считаться обрывом

Сценарий не считается обрывом после диалога, если:

- клиент был занят
- попросил вернуться позже
- менеджер согласовал повторный контакт
- разговор завершился корректно

Это трактуется как содержательный звонок с переносом, а не как обрыв.

## Встреча

### Что считается встречей

Система считает встречей только явный синхронный следующий шаг:

- очная встреча
- онлайн-встреча
- консультация / созвон, если она предложена как явный синхронный слот

### Что не считается встречей

Не считается встречей:

- “оставлю обратный звонок”
- “обратитесь в отдел продаж”
- “скину информацию”
- “направлю материалы”

Если есть только такие действия, встреча считается не предложенной.

### Типы встреч

- `onsite`
- `online`
- `both`
- `none`

### Согласованная встреча

Встреча считается согласованной, если:

- менеджер предложил её явно
- клиент дал согласие
- или явно согласовал дальнейший синхронный слот

## Исходы по встрече

Для управленческого отчёта выделяются три основных сценария:

1. встреча предложена и согласована
2. встреча предложена, но не согласована
3. встреча уместна, но не предложена

Отдельно выделяется сценарий:

4. клиент пока не готов к встрече в первом разговоре

Важно:

- этот сценарий не означает завершение работы менеджера
- менеджер должен продолжать работу через follow-up, перезвон, повторное касание и возврат к следующему целевому действию
- поэтому такой звонок не равен прямому резерву, но и не снимает ответственности за дальнейшую конверсию

## Оценочный резерв

`Оценочный резерв` — это не жёсткий факт упущенной конверсии.

Это ориентир по звонкам, где:

- встреча была предложена, но не согласована
- или встреча была уместна, но не предложена

Оценочный резерв используется для:

- управленческой оценки
- coaching-выводов
- оценки потенциала улучшения конверсии

При этом сценарий `клиент пока не готов`:

- показывается отдельно
- не включается в резерв один к одному
- но обязательно учитывается как зона дальнейшей работы менеджера и дисциплины follow-up

## Исключения из KPI основной воронки

В KPI основной воронки не должны входить:

- нецелевые звонки
- сервисные звонки
- звонки, прерванные не по вине менеджера
- звонки `callback later`, если предметного диалога не было

## Оценка менеджера

Оценка менеджера строится по этапам продаж и не заменяется только фактом встречи.

Смысл:

- встреча = один из ключевых исходов
- этапы = объяснение, почему исход получился

## Экспертная верификация

Статус `Требует экспертной верификации` ставится, если:

- неуверенно распознан ЖК
- спорен факт встречи
- факты противоречат друг другу
- транскрипт явно низкого качества
- логика не может сделать надёжный вывод

Такие звонки:

- не должны молча искажать KPI
- должны быть видны отдельно

## Нормализация ЖК

Система использует:

- базовый словарь ЖК
- алиасы
- пост-нормализацию после транскрибации

Если уверенность низкая:

- система не должна молча подставлять случайное название
- звонок должен получать признак экспертной верификации

## Клиентская и внутренняя версии

### Клиентская версия

Должна показывать:

- результат по воронке
- встречи
- резерв
- ключевые причины потерь
- экспертную оценку звонков

### Внутренняя версия

Может дополнительно показывать:

- больше флагов
- больше диагностических причин
- больше технических пояснений

## Приоритеты продукта

На текущем этапе приоритеты такие:

1. корректность статуса звонка
2. корректность логики встречи
3. честность исключений из воронки
4. понятность клиентского отчёта
5. устойчивость нормализации ЖК

## Граница серьёзного продукта

Система считается серьёзной рабочей моделью, когда:

- методология зафиксирована
- спорные звонки не скрываются
- исключения не портят KPI
- встреча детектируется стабильно
- отчёт понятен без устных пояснений
- логика проходит расширенную проверку на нескольких застройщиках
